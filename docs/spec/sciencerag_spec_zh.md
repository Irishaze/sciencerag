# ScienceRAG 整体设计规范 — TEC 世界模型闭环架构

## 1. 目的与范围

本规范描述 ScienceRAG 在 TEC 世界模型闭环架构中的完整设计,覆盖它在流水线中的全部四个接入点:

1. **前置文献检索**:在 Hermes 智能体编译实验规范之前,为其提供有文献依据的实验先验(即开始仿真前就能从文献与历史数据中知道的背景知识,如合理的参数取值范围、材料属性、预期性能区间,用于约束实验规范,避免从零盲猜)。
2. **验证与学习**:对仿真结果做异常检查与科学评估,并产出模型微调建议与知识库更新候选(即架构图中 "ScienceRAG 科学验证与学习" 的四个子模块)。
3. **报告生成**:输出带引用、可审计的实验报告。
4. **图谱问答**:支持用户基于科学知识图谱提问(GraphRAG,类 MiroFish 模式)。

不在范围内:Hermes 智能体本身、仿真适配器,以及第 02 部分的治理流程(验证与版本治理、模型与参数注册)。本规范将它们视为 ScienceRAG 输出的调用方或审批方:ScienceRAG 负责"提出",治理流程负责"批准"。

## 2. 总体架构与设计原则

ScienceRAG 是一组供 Hermes 调用的服务端点(endpoint,即服务对外暴露的可调用接口;每个端点对应一项独立能力,有固定的地址、输入格式与输出格式,Hermes 像调用工具函数一样按需请求),自身从不承担编排职责。四个端点按流水线顺序为:

`sciencerag.priors`(规划前) → `sciencerag.validate`(仿真后) → `sciencerag.report`(验证后) → `sciencerag.ask`(随时,面向用户)

贯穿所有组件的三条原则:

**严格结构化输出。** 所有响应在返回前经过 schema 校验,因此智能体绝不需要解析自由文本。校验失败时返回类型化错误,绝不返回不完整的 JSON。

**凡论断必有来源。** 每一条科学论断都携带来源引用:论文 DOI、知识图谱三元组 ID,或仿真运行 ID。

**只提议,不直写。** ScienceRAG 产出的任何内容都不直接写入知识图谱或模型注册表;所有知识与模型更新一律打包为候选更新包,经由第 02 部分的「离线验证 → 人工审批 → 注册/回滚」路径落地。

## 3. 组件 A — 前置检索(`sciencerag.priors`)

### 3.1 角色

由 Hermes 在任务规划阶段调用,时机在意图理解之后、结构化实验规范编译之前。职责是将研究问题转化为结构化的实验先验:合理的参数范围、材料属性、已知的标度关系,以及候选配置,每一项都以检索到的文献或内部知识图谱为依据。

### 3.2 检索流水线

内部流程遵循 PaperQA2 模式:查询分解 → 混合检索(稠密向量 + 关键词)覆盖论文库与科学知识图谱 → 逐块相关性打分的证据收集 → 结构化综合。知识图谱享有最高查询优先级,因为它包含系统自身历史运行的发现,而这是任何外部语料库都不具备的。优先级指查询顺序而非依赖:冷启动阶段图谱为空或极稀疏时,图谱查询命中 0 条,检索自动落到论文库与外部来源,端点照常返回(此时先验全部来自文献,`coverage` 中如实反映)。图谱随仿真运行与审批入库逐步积累。可选的冷启动加速("播种"):不等仿真攒数据,先跑一个一次性批处理任务,让 LLM 通读内部论文库,把文献中的关键结论逐条抽取成三元组(例如从某篇论文抽出"Bi₂Te₃ 薄膜在 300K 工况下 COP 达 1.5",来源挂该文 DOI),作为候选提交人工审批后入库。流程完全复用 4.4 已定义的"候选 → 审批 → 入库"路径,不引入新机制。效果是图谱从第一天起就有文献级的基础内容,`ask` 端点与 Web 前端上线即可用,不必空转等待仿真积累。

语料来源按优先级排列:内部知识图谱、内部论文库(项目维护的 TEC 文献集)、外部检索(Semantic Scholar / arXiv API)作为内部覆盖不足时的补充。外部结果标记为 `provenance: "external_unverified"`,以便下游按可信度加权处理。

### 3.3 工具接口

请求:

```json
{
  "query": "Bi2Te3 薄膜 TEC 中 COP 与热电臂几何的关系",
  "task_context": {
    "objective": "maximize_cop",
    "constraints": {"heat_load_w": 5, "ambient_k": 300}
  },
  "max_priors": 5,
  "allow_external": true
}
```

响应:

```json
{
  "status": "ok",
  "priors": [
    {
      "prior_id": "pr_2026_0713_001",
      "kind": "parameter_range",
      "field": "leg_length",
      "value": {"field_name": "leg_length", "min": 0.02, "max": 0.2, "typical": 0.06, "unit": "mm"},
      "confidence": 0.82,
      "sources": [
        {"type": "paper", "doi": "10.1234/example", "span": "p.4, Fig.3"},
        {"type": "kg_triple", "triple_id": "kg_88213"}
      ],
      "notes": "臂长偏短有利于功率密度;COP 在中段区间达到峰值。"
    }
  ],
  "coverage": {"internal_hits": 7, "external_hits": 2, "gaps": ["接触电阻数据稀缺"]},
  "trace_id": "tr_..."
}
```

`kind` 为枚举类型:`parameter_range`(参数范围)、`material_property`(材料属性)、`scaling_relationship`(标度关系)、`candidate_config`(候选配置)、`caution`(注意事项)。`gaps` 字段是刻意设计的:Hermes 需要知道文献中*未*覆盖的部分,从而在这些区域扩大仿真扫描范围,而不是盲信一个证据薄弱的先验。`field` 与可选字段 `related_fields` 的取值均来自仿真参数契约(见 3.6);`material_property` 保留枚举值但因材料固定而实际不产出。

### 3.4 与假设排序的配合

若团队采用类 AI co-scientist 的「生成—辩论—排名」竞赛机制,竞赛逻辑归属于 Hermes(或其平级工具),而非本服务。本服务通过批量证据请求为其提供支撑:给定 N 个候选实验规范,逐一返回支持性与反驳性证据,使排序器(Elo/BTL)能够基于文献依据而非模型直觉来打分。

### 3.5 论文库入库流程

内部论文库通过一条离线入库流水线维护,与在线端点分离,按批运行:

1. **收集**:两个来源。团队手动加入的文献(共享目录或上传入口);以及组件 A 外部检索(Semantic Scholar / arXiv)命中的文献。v1 简化后的实际实现(`sciencerag/priors/external_retrieval.py`、`arxiv_retrieval.py`):只要能拿到真实全文 PDF(arXiv 恒有;Semantic Scholar 命中里带 `openAccessPdf` 的开放获取论文),就直接下载进 `corpus/papers/`,PaperQA2 下次查询自动增量索引——从那一刻起这篇论文就是普通的、`provenance="internal"` 的语料库内容,**没有中间的"待审批/待转正"状态**。原先设想的"人工确认或预设规则自动转正"两条路径在 v1 未实现,也不打算实现——下载到的全文直接可信,不额外降权 confidence。唯一仍标 `provenance="external_unverified"` 的情形是 Semantic Scholar 命中但拿不到开放全文的论文(付费墙),这时只能退回摘要级证据,标签反映的是"证据单薄",不是"来源不可信"。
2. **解析**:从 PDF 抽取正文、章节结构与元数据(标题、作者、年份、DOI)。v1 仅支持文字版 PDF,扫描版拒收并记录日志。
3. **切块**:按章节边界切分为数百 token 的片段,相邻片段留重叠;每个片段携带元数据(DOI、页码、章节),这是响应中 `sources` 能精确定位到页与图的前提。
4. **向量化入库**:片段经 embedding 模型转为向量,连同原文与元数据存入向量库;按 DOI 去重,重复上传只更新。

约束:embedding 模型版本与向量库绑定记录;更换模型时必须全库重建,禁止新旧向量混存。入库流水线的运行记录(何时入了哪些文献、解析成功/失败)纳入审计日志。

### 3.6 仿真参数契约(sim_params.json)

先验的 `field` 并非自由文本:它的取值空间由一份与仿真侧(COMSOL 单级 Bi2Te3 TEC)对齐的参数契约 `sim_params.json`(`sciencerag/priors/sim_params.json`)固定,避免 Hermes 在把先验填入仿真时还要做一次名称/单位翻译——例如先验侧曾自造 `leg_length_um` 这样的命名,仿真侧实际叫 `leg_length` 且单位是 mm,人工翻译容易出错,也让先验与仿真结果按参数对比时对不上。

契约把仿真参数分为五类,并各自标注 `prior_target`:

- **`geometry_free`(自由几何参数,`prior_target: true`)**:Hermes 主动优化/扫描的对象,是先验唯一的目标,共 12 个——`leg_length`、`leg_width`、`pitch`、`d_conductor`、`d_ceramics`、`length`、`width`、`height`、`sink_base_h`、`sink_fin_h`、`sink_fin_w`、`sink_fin_n`,每个参数带真实仿真参数名与单位。
- **`material`(材料,`prior_target: false`)**:材料固定为 Bi2Te3,属性(Seebeck 系数、电阻率、热导率、优值 Z)随温度变化,按 200–400K 的整张表登记为已知常量;先验不对材料出建议。
- **`operating_condition` / `derived` / `numerical_setting`(均 `prior_target: false`)**:分别是任务给定的工况、由其他参数算出的派生量、纯数值求解设置,均与先验无关。

`Prior` 模型上,单参数先验(`parameter_range`/`caution`)用 `field`;新增的可选字段 `related_fields`(默认空列表,向后兼容)供多参数先验(`scaling_relationship`/`candidate_config`)表达"一组参数"或"参数之间的关系"。两者取值都必须 ∈ 契约 `geometry_free` 的参数名集合,抽取流水线在解析 LLM 输出后强制校验,不在集合内一律拒绝——防止 LLM 自造名称,或误碰材料/工况/派生参数。抽取本身也是目标导向的:提示词把这 12 个参数名与单位直接列给 LLM 作为清单,而非任其自由命名;参数之间的关系不预设分组,只有证据里实际提到才抽成 `scaling_relationship`,文献没提就不造。

`kind` 五值枚举本身不变,但 `material_property` 在当前项目实际上是"存在于枚举、但从不产出"的状态:材料固定且属性已知,先验不对它出建议;若 LLM 仍误输出材料类先验,抽取流水线会将其过滤,不进入响应,但计入审计日志(而非 `coverage.gaps`——这不是"漏检覆盖",而是"被正确排除")。

`coverage.gaps` 同样以契约的 12 个几何参数为标尺:本次抽取覆盖了哪些、没覆盖哪些,没覆盖的进 `gaps` 而不是硬凑一个先验去凑数。三级归因(未检索到证据 / 检索到但相关性不足 / 抽到但未进入最终结果)已实现(`retrieval.py` 的 `_build_geometry_gaps`)。**"抽到但未进入最终结果"这一档,2026-08-05 起不再是"置信度不足"**——置信度公式停止充当筛选关卡(见 §3.7),真正的筛选权交给 §3.9 的语义支持判断:这一档现在对应"被判 REVIEW 排除"或"通过了 max_priors 上限截断"两种情况,`coverage.gaps` 里 `_build_gaps`/`_build_max_priors_gap` 各自给出具体原因,`_build_geometry_gaps` 只负责标注"某个参数属于这一档",不区分具体是哪一种。"相关性不足"这一档由 `_match_params_to_evidence` 判定:对本次查询中被 `MIN_EVIDENCE_RELEVANCE` 筛掉的证据、以及尚未通过前两档解释的参数,一次批量 LLM 调用(而非逐参数调用,受 §8 单次查询延迟预算约束)读原文判断每条被筛掉的证据是否真的在讨论某个具体契约参数,而不是像早期版本那样靠关键词重合近似判断——后者会把"fin height"(散热片翅片高度)误判成命中了不相关的契约参数 `height`(整机高度)这类同词不同指的假阳性。上游检索环节本身不记录"这条证据是关于哪个契约参数",LLM 调用失败时退化为原关键词重合启发式(`_keyword_fallback_match`)兜底,不让这一档的暂时故障拖垮整个请求;正常路径下不再依赖它。

五种 `kind` 在契约体系下的填法:

| kind | field | related_fields | value 要点 |
|---|---|---|---|
| `parameter_range` | 恰好一个契约参数名(必填) | 不填 | `field_name`(必填,须与上面的 `field` 完全一致)、`unit`(必填)、`min`/`max`/`typical` 至少一个、可选 `conditions` |
| `material_property` | 恒为 `null` | 不填 | 材料属性固定见契约,不由先验提供;实际不产出 |
| `scaling_relationship` | `null` | 关系涉及的两个参数(恰好两个) | `x`/`y`(必填,须恰好等于 `related_fields` 的两个参数名)、`direction`(必填,`positive`/`negative`/`convex`/`concave`/`non_monotonic`/`unknown`)、可选 `functional_form`/`validity_range` |
| `candidate_config` | 恒为 `null` | 这组配置涉及的参数列表(至少两个) | `parameters`(必填,键须恰好等于 `related_fields`,值为每个参数在这组配置里的取值)、可选 `reported_performance`/`context` |
| `caution` | 通常填一个参数;涉及多参数时用 `related_fields` | 视情况 | `statement`(必填,限制/注意事项本身)、可选 `applicability_scope`(成立的条件) |

`value` 不是自由 dict——每个 `kind` 对应一个专属 Pydantic 模型(`sciencerag/priors/models.py`),字段固定,不接受 `summary` 这类自由文本兜底键;抽取不出结构化内容宁可不产出这条先验,也不允许拿一句话糊弄过去。`value` 内部命名参数的字段(`field_name`/`x`,`y`/`parameters` 的键)必须与外层 `field`/`related_fields` 完全一致,由 `Prior` 自身的校验强制保证——两边分别来自 LLM 的同一次输出,理论上不该打架,但没有校验就没法排除 LLM 自相矛盾的可能。

### 3.7 阈值调优方法论(检索 k / 证据相关性 / 先验置信度)

检索流水线有两道独立的**筛选关卡**:检索侧的 top-k 截断、证据相关性阈值 `MIN_EVIDENCE_RELEVANCE`。某个契约几何参数在某次查询中"没有先验",可能来自不同原因——文献本身没有相关内容(真 gap,应保留,是留给 Hermes 扩大仿真扫描的有效信号);或文献本有相关内容,却被 k / 相关性中的某一关卡筛掉(假 gap,应通过校准各关卡消除,而不是靠调低阈值把噪声一并放进来)。两道关卡各自独立调优,不能用后一道关卡的阈值去补前一道关卡的问题。

调优顺序:先放开检索侧的 top-k(用不同 k 下 12 个几何参数的覆盖率曲线找拐点,而非盲目调大——k 越大,进入摘要/抽取阶段的候选证据越多,成本与噪声也随之上升);再在新 k 与目标导向抽取(见 3.6)下重新采集探针数据,保留每条证据/先验筛选前的原始分数(不因阈值静默丢弃,否则无法回溯误杀);再校准相关性阈值,采用"独立 LLM 裁判"方法——对处于阈值边界带的证据样本,由与生产链路模型无关的裁判模型(GPT-4o,`temperature=0`,保证可复现)逐条判定应保留还是丢弃,裁判规则须能识别"证据实为参考文献列表标题、并非论文正文"这类已知的误报模式,再按分数分桶统计误判率曲线,在"漏检率"与"噪声纳入率"之间取平衡点。全程用真实数据验证,不凭经验直接定阈值;探针与裁判所需的记录只在启用 trace 的探针路径中产生,生产查询路径的行为不变。

`coverage.gaps` 最终应对每条未覆盖参数标注筛选层级归因(未检索到证据 / 检索到但相关性不足 / 抽到但未进入最终结果),使 Hermes 能区分"真无先验"与"流水线筛掉的弱信号",而非把两者混为一谈的笼统"未覆盖"。

**k-sweep 复验(2026-08-03)**:`EVIDENCE_K=20` 原是在 `MIN_EVIDENCE_RELEVANCE=0.7`(早期值)下测出的覆盖率拐点,relevance 两次下调后未曾复验。在当前 relevance=0.5 下用完整 40 次真实调用重新测过(`data/k_sweep_results.json`,原 relevance=0.7 数据存档在 `data/k_sweep_results_relevance_0.7_2026-07-31.json` 供对照):覆盖率曲线变平——k=10/20/30/50 对 12 个参数全部 12/12 覆盖,原先 k=10→9/12 的差距消失了,靠覆盖率这个指标本身已经区分不出该留 k=20 还是降到 k=10。但原始证据/先验量仍随 k 明显增长(k=10 时 10 条查询合计 49 条证据/34 条先验,k=50 时 106/69)——覆盖饱和不代表"多来源印证的冗余度"也饱和,后者对置信度排序仍有意义(见下)。因此暂未下调 `EVIDENCE_K`(详见 `retrieval.py` 里 `EVIDENCE_K` 上方注释)。

**置信度:从"筛选关卡"降级为"纯排序信号"(2026-08-05 定案)**。`CONFIDENCE_THRESHOLD` 已移除,`confidence` 不再决定一条先验进不进最终结果——这个判断权已经转移给 §3.9 的语义支持判断。原因是三轮独立验证,一致指向同一个结论:置信度公式的输入(来源论文数、平均检索相关度)结构上就不携带"这条先验的内容对不对"这个信息,不管怎么调公式形状都测不出来——

- 早期(n=34):把 `n_papers`/`avg_relevance` 跟独立裁判的 SUPPORTED/USEFUL 判定连起来看,没有单调关系。
- 开源幻觉检测模型 Vectara HHEM 独立验证(n=33):同样没有区分度。
- 2026-08-04 的正式对比(k/relevance/confidence 计划 Part 2,`scripts/confidence_formula_probe.py`):在 Phase B3 数字溯源校验已上线、DROP 构成更干净的 48 查询/22 判定样本上,对比了 4 个候选——noisy-OR 概率组合(候选 A)、A×跨来源数字一致性(候选 B)、现有加法公式原样(候选 C,对照组)、独立 LLM(luna)直接打 0-1 连续分(候选 D)——没有一个测出比现有公式更好的区分度。样本量小是一部分原因(n=22,仅 3 条 DROP),但也有结构性原因:noisy-OR 只要引用证据里有一条打满分就封顶到 1.0(这批数据里 22 条有 11 条卡在满分),"多来源印证"这个卖点根本没被真正考验过;候选 D 打分高但实际 DROP 的案例,原因都是"文不对题""太笼统",不是"证据强度不够"——这类问题不管用公式还是连续打分衡量"证据支持强度"都测不到,因为问的根本不是同一个维度。

**结论采用候选 C(现有加法公式,不改常数、不重新拟合)**,继续作为已通过质量检查的先验之间的排序键;`max_priors` 超出上限时依据它截断。真正负责"这条先验对不对"的判断,交给下面 §3.9 新增的语义支持判断阶段。

### 3.8 数字溯源校验(numeric groundedness)

3.7 的两道关卡都是**分数型软阈值**,负责排序与取舍;但它们结构上都测不出"这条先验里的数字是不是编的"——DROP 的主因(数字幻觉)需要真的去读证据原文核对,不是任何 metadata 代理指标能测出来的(见 3.7 的三轮验证)。为此单独加了一道**确定性、在线、每条必过**的硬校验,跟 3.7 的软阈值并列但独立:

- 检查内容:先验 `value` 的数值字段(`min`/`max`/`typical`/`magnitude`/`parameters`/`reported_performance`/`conditions` 里的数字)、`notes`,以及五个 `kind` 里所有的自由文本字段——`caution` 的 `statement`/`applicability_scope`、`scaling_relationship` 的 `functional_form`/`validity_range`(2026-08-05 补齐,此前这两个 kind 的自由文本完全不扫描数字,曾被真实数据抓到过一次编造数字从这个漏洞溜过去,见下方"曾发现的漏洞")。每一个数字都必须能在其引用证据的合并原文里找到匹配——精确相等,或相对误差 ≤2%(容忍 LLM 抄证据时的四舍五入,如证据 1.83 → 先验 1.8)。
- **v1 不做跨单位换算**(20 µm 与 0.02 mm 视为不匹配)——刻意保守,换算表是无底洞;为此在抽取提示词里加了一条规则,要求 LLM 保留证据原文使用的单位,不要自行换算或折算。
- 任一数字找不到匹配 → 该先验整条拒收,拒收原因(格式 `"{field}: {数字} not found in {证据编号}"`)记入 trace 的 `numeric_check_failures` 字段,并走既有的重试机制(把失败原因喂回 LLM);重试耗尽则该条先验丢弃,计入 `coverage.gaps`。
- 顺序上,这道校验在 `Prior` 的 Pydantic 结构校验(3.6 的契约字段名、value 子 schema 等)通过之后、3.9 语义支持判断之前生效——数字造假比语义层面的问题更便宜、更确定地能查出来,先拦掉能省下一次语义判断的调用。
- 实现细节(容易被后续重构不小心破坏,记录在此):文本抽数字时会自动排除紧跟在字母后面的数字(如"Bi2Te3"里的 2、3),否则材料化学式会把每一段证据都污染出一堆假"证据数字",让不相关的先验数字"2"或"3"因为凑巧撞上化学式而误判为已溯源。这条规则不会挡住"数字紧跟单位、中间没空格"的常见写法(如"60um"),只挡数字前面紧跟字母的情况。
- **曾发现的漏洞(已修复)**:`caution` 类型的先验一度完全不扫描其 `statement`/`applicability_scope` 字段(当成纯文字处理)。2026-08-04 用 luna 与 GPT-4o 的裁判交叉验证真实生产数据时,发现一条先验的 `statement` 断言"需要约 90 K 温差",这个数字在引用证据全文里根本不存在,却因为这个漏洞顺利通过了校验——已修复。

### 3.9 语义支持判断(semantic support judgment)

数字对得上不代表内容就对——"文不对题"(如引用热电**发电**器研究支持热电**制冷**器的论断)、"太笼统没有实际信息量"、"凭空发明因果关系"这几类问题,3.8 的规则匹配抓不到,需要真的读懂证据原文才能判断。为此在数字溯源校验之后加了一道独立 LLM 裁判(`gpt-5.6-luna`,Phase C 裁判打擂选出、并于 2026-08-04 用真实生产数据交叉验证过——跟另一个独立裁判 GPT-4o 在 22 条真实先验上一致率 81.8%,还真的抓到 2 条 GPT-4o 本身漏判的幻觉),对每条已通过数字校验的先验草稿判定 SUPPORTED + USEFUL:

- **批量调用,不逐条**:一次查询里所有通过前两关的先验草稿,一次性交给裁判模型判完,而不是每条先验单独调用一次——受 §8 单次查询延迟预算约束,这个原则跟 §3.6 `coverage.gaps` 相关性归因那道 LLM 调用是同一个考量。
- **三档判定,不是二元**:
  - `KEEP`:证据原文直接、字面支持先验的每个论断。
  - `REVIEW`:先验对证据的表述做了标准的领域知识翻译(例如证据说"高纵横比",先验把它映射到 `leg_length`/`leg_width`——纵横比本来就是长宽比的定义,不是编造),不是字面照抄,但也不是无中生有。
  - `DROP`:证据不支持、矛盾、文不对题,或论断太空泛没有实际信息量。
- **DROP 会重试,REVIEW 不会**:`DROP` 判定使整个抽取尝试失败,走跟数字校验一样的重试机制(把裁判给出的原因喂回 LLM,让它重新起草)——同一批草稿里任意一条被 DROP,整批都重来,这是延续数字校验已有的重试粒度,不是本次新引入的设计。`REVIEW` 不触发重试——同一份证据不会因为再抽一次就变得更"字面直接",重试没有意义;`REVIEW` 判定的先验被直接排除出最终结果,通过 `ExtractionResult.review_priors` 上报给 `coverage.gaps`(见 3.6/3.7),而不是像 `DROP` 一样静默重来。
- **判断范围只限于这条先验自己引用的证据**,不是整批证据——裁判提示词里每条证据片段都带着编号标注来源(复用抽取提示词已有的 `[E1] (source: doi, span) "..."` 格式),避免像候选 D 打分实验里那样因为证据没标来源、裁判判断不出"多来源是否互相印证"。
- 任何调用失败(网络错误、裁判输出格式不对、裁判漏判了某条先验)都统一包装成跟数字校验一样的重试路径,不会让一次瞬时故障直接打断整个请求。

## 4. 组件 B — 验证与学习(`sciencerag.validate`)

对应架构图中「ScienceRAG 科学验证与学习」的四个子模块。调用时机在潜在世界状态创建之后:即一次运行走完 04 仿真 → 05 结果标准化 → 06 潜在状态编码全部三步后,由 Hermes 调用一次。定在这个时点是因为三类异常检查中,守恒与 PDE 残差只依赖 05 的标准化结果,而 OOD 检测必须依赖 06 产出的潜在状态 z;以最晚的依赖为准、单次调用,架构最简。四个子模块按固定顺序运行,前一级是后一级的门槛:

异常检查 → 结果评估 → (并行)模型微调建议 + 知识库更新 → 组装候选更新包

### 4.1 异常检查

**职责:** 判断这次运行的结果在物理上是否可信,不可信的结果不允许进入任何学习环节。

三类检查依次执行:

1. **守恒检查**:对温度场与热流场做能量平衡核算,残差超出阈值即告警。
2. **PDE 残差**:将求解结果代回控制方程(热电耦合 PDE),计算残差范数,用于捕捉"收敛了但收敛到错误解"的情况。
3. **OOD 检测**:将本次运行的潜在状态 z 与历史运行分布对比(马氏距离或基于密度的评分),显著偏离即标记为分布外。分布外不等于错误,但意味着代理模型的预测在此不可信,需降权处理。

**输出:** 类型化的异常列表,每条含 `check`(检查项)、`severity`(`info` / `warning` / `blocking`)、`evidence`(具体数值与阈值)。任何 `blocking` 级异常都会短路后续所有环节:运行结果只进入报告(标注失败原因),不产出微调建议,不产出知识候选。这条规则是本组件最重要的设计决策:宁可少学,不可学错。

### 4.2 结果评估

**职责:** 通过了异常检查的结果,进一步回答"这个结果科学上说得通吗"。

两条对照线:

1. **基准对比**:与基准数据库中的已知案例(解析解、高保真 FEniCSx 参考解、实验数据)对比,量化偏差。
2. **先验对比**:与组件 A 在规划阶段提供的文献先验对比。结果落在先验范围内,是一次常规确认;结果显著偏离先验,则是本次运行最有信息量的发现,需要在输出中显式标出并附上双方证据(先验的文献来源 vs 本次运行的数据),交给人来裁断是"文献错了 / 先验检索有偏 / 仿真有问题"。这一步是前置检索与后置验证之间的闭环,也是整个 ScienceRAG 设计里检索真正产生科学价值的地方。

**输出:** 评估结论(`consistent` / `deviation_found` / `insufficient_benchmark`)、逐项偏差数据、证据引用。

### 4.3 模型微调建议

**职责:** 面向代理模型(PhysicsNeMo 系的 SepONet / FNO / MeshGraphNet 等)提出改进建议;只提建议,不执行训练。

依据两类信号选样:代理模型预测与高保真求解结果偏差最大的区域(误差驱动),以及 OOD 检测标记的分布外区域(不确定性驱动,即主动学习的思路)。建议内容包括:推荐纳入训练集的样本清单(以运行 ID + 区域标识表示)、建议的损失加权、超参数调整方向及理由。

**输出:** 微调提案,进入候选更新包的 `surrogate_update` 字段。是否执行、何时执行,由第 02 部分的治理流程与人工审批决定。

### 4.4 知识库更新

**职责:** 从通过评估的运行结果中抽取候选三元组(材料—结构—工况—性能),供知识图谱审批入库。

流程:从结果与评估结论中抽取候选关系 → 与图谱中现有三元组做去重与冲突检测(同一关系已存在且一致 → 仅追加来源;存在但数值冲突 → 标记冲突,双方来源并列呈现,不自动覆盖)→ 为每条候选附上完整溯源(运行 ID、置信度、支撑数据切片),即架构图中的「来源审查」所需材料。

**输出:** 候选三元组列表,进入候选更新包的 `kg_candidates` 字段。与组件 D 的只读约束呼应:写入图谱的唯一路径是审批通过。

### 4.5 组件接口(概要)

请求:`run_id` + 标准化结果引用 + 潜在状态引用 + 本次运行使用的 `prior_id` 列表。响应:

```json
{
  "status": "ok",
  "anomalies": [{"check": "energy_balance", "severity": "warning", "evidence": {...}}],
  "evaluation": {"verdict": "deviation_found", "deviations": [...], "sources": [...]},
  "update_package": {
    "surrogate_update": {...},
    "kg_candidates": [...],
    "blocked": false
  },
  "trace_id": "tr_..."
}
```

`blocked: true` 时 `surrogate_update` 与 `kg_candidates` 必为空,这是 schema 层面强制的不变量,不依赖调用方自觉。

## 5. 组件 C — 报告生成(`sciencerag.report`)

在验证完成后调用。输入包括标准化结果、组件 B 的完整输出(异常、评估、更新提案),以及规划阶段使用的先验。输出一份 JSON 文档外加渲染后的 Markdown/PDF 视图。

必备章节:系统所理解的目标与约束;实验规范摘要;带不确定度的关键结果;与文献先验的对比(直接引用组件 B 4.2 的评估结论);异常与注意事项;更新提案摘要(本次运行建议了哪些微调与知识候选,便于审批者从报告直达审批);完整引用列表。报告正文中的每一条定量论断都附带指向运行 ID 或文献来源的行内引用。报告随运行血缘版本化存储,使第 02 部分的注册表能够将模型更新回溯到促成它的那份报告。

## 6. 组件 D — 图谱问答(`sciencerag.ask`)

### 6.1 知识图谱

复用现有科学知识图谱的 schema:实体为材料、结构、工况与性能指标;边为带类型的关系,每条边携带来源(论文 DOI 或运行 ID)与置信度。v1 无需修改 schema。

### 6.2 查询流程

类 MiroFish 模式:用户提问 → 实体/关系抽取 → 图谱遍历组装相关子图 → 子图与问题一并送入 LLM 进行有据可依的答案合成 → 返回答案并附带子图,供前端渲染「依据是什么」(关系可视化、来源·置信度)。若图谱覆盖不足,服务如实说明,并可选择回退到组件 A 的文档检索,回退情况在响应中明确标注。

### 6.3 写入路径(关键约束)

`sciencerag.ask` 与 `sciencerag.report` 对图谱均为只读。新知识进入图谱的唯一路径是组件 B 4.4 产出的候选三元组通过验证与版本治理。这一约束防止单次异常运行污染所有后续检索,相当于「静默解析 bug 向下游扩散」这一问题在知识层面的对应物。

## 7. 呈现层 — 交互式 Web 前端(类 MiroFish)

组件 C 与 D 的用户入口是一个 Web 应用(Vite/React 前端 + Flask/FastAPI 后端,后端仅做端点转发与会话管理)。页面分三个区域:

1. **问答面板**:用户提问,调用 `sciencerag.ask`。
2. **图谱可视化**:渲染 `ask` 返回的子图(力导向布局,节点可点击查看来源与置信度),用户提问后相关子图高亮,直观呈现「答案依据是什么」。
3. **报告面板**:按运行血缘浏览与导出历史报告。
~~4. **文献审批面板**:处理 3.5 节的外部文献转正队列~~——**已废弃,不实现**:3.5 节描述的外部文献转正队列(人工确认/预设规则自动转正)在 v1 简化后不存在了,下载到的开放获取全文直接可信,没有待审批状态,自然也没有面板可做。`scripts/approve_external_papers.py` 已删除。

注意:图谱本身由仿真闭环持续积累产生,提问只是从全图中提取并展示相关子图,前端不创造知识。三个面板(问答、图谱可视化、报告)全部只调用只读端点,不涉及任何写入或审批操作(三元组入图谱与模型微调的审批属于第 02 部分的验证与版本治理,不在本前端范围内)。可选扩展:针对一段问答会话生成小结报告,复用 `report` 的引用机制。

## 8. 通用要求

四个端点均返回经 schema 校验的 JSON,并携带 `trace_id`,将请求、证据与响应串联以供审计。错误采用类型化定义(`retrieval_timeout`、`schema_validation_failed`、`insufficient_coverage`、`benchmark_unavailable` 等),使 Hermes 能够确定性地分支处理。

延迟目标:`priors` ≤ 30 秒(阻塞规划)、`validate` ≤ 60 秒(阻塞闭环推进,其中守恒/残差检查为主要开销)、`ask` ≤ 10 秒(交互式)、`report` 为尽力而为的批处理。

评估机制是维护一套固定的回归测试集:检索侧为(查询 → 带已知来源的预期先验/答案),验证侧为(已知有缺陷的历史运行 → 预期异常判定,含应当 `blocking` 与不应误伤的两类案例)。度量引用准确率、覆盖率、schema 合法率,以及异常检查的查全/查准;每次修改提示词、检索参数、阈值或语料库后必须运行。

**已知的方法论限制(2026-08-02 发现)**:少数几个查询主题在语料库覆盖本来就稀薄(比如具体的散热片鳍片尺寸、电池热管理专用配置),同一个 fixture 在语料库和代码都不变的情况下反复重跑,先验产出量能在 0 到数条之间大幅波动。查过根因,是 PaperQA2 负责"要不要再搜一轮、换什么词重搜、什么时候算够了"的 agent_llm 工具选择循环本身运行间不稳定,不是我们自己的抽取逻辑(那部分一直是 `temperature=0`)。试过给 agent_llm 传固定 `seed`(OpenAI 支持、litellm 能透传),实测同一查询连跑 3 次先验数仍是 0/1/0,没有解决——`seed` 只是"尽力而为"的确定性,对多步 agent 决策链没有硬保证。目前的应对是把这几个 fixture 标记为 `known_flaky`(`sciencerag/priors/regression.py`),`run_regression.py` 对它们跑 3 次取多数结果,而不是相信单次结果。这不是修复了不确定性,只是不让已知的、跟代码质量无关的检索噪声污染回归判断。

## 9. 待确定的问题

以下按 M2-M6 实现完成(2026-08-05)后的状态更新,标注哪些已有具体答案、哪些仍然开放。已有答案的不代表"定案不可改",而是"现在有一份可以拿去复核/讨论的具体实现",不再是纯设计阶段的空白。

- **外部检索:是否需要?用哪些 API?** 已实现(M6,`sciencerag/priors/external_retrieval.py` + `arxiv_retrieval.py`):Semantic Scholar 免费搜索 API + arXiv 免费 Atom API,只在内部检索覆盖不足时触发。命中论文只要有开放获取全文(arXiv 恒有;Semantic Scholar 靠 `openAccessPdf` 字段判断)就下载真实 PDF 直接存进 `corpus/papers/`,由 PaperQA2 正常索引、正常检索,不再是摘要级证据;下载后即视为可信,没有审批/转正队列(`scripts/approve_external_papers.py` 连同待审队列机制已删除——团队判断这一层复杂度不值得,宁可简单)。Semantic Scholar 命中若拿不到开放全文(期刊白名单/付费墙判定因此也不再需要)则退回摘要级证据,标 `provenance="external_unverified"`。两个 API 都有限流风险(Semantic Scholar 实测遇到过 429),均已做优雅降级(跳过外部增强,不影响内部结果返回),不是硬依赖。
- **ScienceRAG 使用哪个 LLM 后端?上下文预算多少?** 部分已定(M1 期间的决定,非本次新定):抽取/摘要用 DeepSeek,embedding 用 OpenAI `text-embedding-3-small`(见 `sciencerag/common/config.py`)。但 PaperQA2 内部的检索 agent(`agent_llm`)切到 DeepSeek 会卡死不收敛(生产环境实测烧了钱才发现),固定使用其默认的 OpenAI 模型——目前没有统一到单一 LLM 后端,是两个后端并存。上下文预算仍未定。
- **组件 A 的先验是强制输入还是仅供参考?** 仍未定。M2/M3 实现里先验是可选输入(不传就跳过先验对比,不报错),但这只是 ScienceRAG 侧的技术容错设计,不代表 Hermes 编排层"应不应该"把先验当强制项——这个决定权在 Hermes,不在本规范范围内解决。
- **4.1 三类异常检查是否合适?请仿真/物理侧同事复核,可替换或补充。** 三类均已实现(`sciencerag/validate/checks.py`)且用真实 COMSOL 数据跑通过,但判定阈值(守恒/PDE 残差用"相对已知基线的倍数",OOD 用"相对训练样本自身离群度的百分位")是工程占位符,未经真实数据校准。现在可以请仿真/物理侧同事对着具体实现和真实输出复核,而不是对着抽象设计复核。
- **4.3 微调建议方案是否有用?请代理模型训练侧同事复核。** 已实现基本版(`sciencerag/validate/finetune.py`):按误差信号(评估偏差)和不确定性信号(warning 级异常)选样,产出建议训练样本、损失加权方向、超参数调整方向。同样需要代理模型训练侧同事对着具体输出复核有效性,当前方案未经该方向同事确认。
- **异常检查阈值由谁定?初值取多少?** 初值已定,但明确是占位符,不是校准值:守恒/PDE 残差检查——超过 11 个已知案例基线最大值的 2 倍记 `warning`,5 倍记 `blocking`;OOD 检测——离群程度超过 31 个训练样本自身分布的 90 百分位记 `warning`,99 百分位记 `blocking`。"由谁定"仍未解决——这些数字是实现时凭经验取的整数,没有走 M1 检索阈值那种"真实数据 + 独立裁判模型标注 + 误判率曲线"的校准流程。**2026-08-15 更新,部分解决**:`sciencerag.validate` 判 `consistent` 用的基准容差(`BENCHMARK_SCALAR_RELATIVE_TOLERANCE`)已经走了真实数据校准——对当前部署的 surrogate 模型做了一次真实留一法交叉验证(`scripts/loo_scalar_error_sweep.py`),发现原来全字段统一 5% 容差与真实模型误差严重不匹配(`delta_T_max_K`/`figure_of_merit_1_per_K` 真实p90误差 <1.5%,而 `total_resistance_ohm`/`optimal_current_A`/`max_heat_dissipation_W` 高达 89%-219%——后三个字段用旧的统一 5% 容差,"consistent" 基本不可能从真实预测里触发),容差和由此产生的 confidence 现在都按字段用真实误差数据校准。OOD 的 `BLOCKING_MARGIN=1.5` 本身仍是占位符,未纳入这次校准。
- **基准数据库现有哪些数据?由谁维护?** 已有答案:tec_surrogate 训练用的 31 条唯一 COMSOL 报告样本(`comsol_report_dataset`)。维护方是 tec_surrogate 项目本身(玉龙),不在 ScienceRAG 范围内维护。样本量小,当前大多数新设计的基准对比会判"证据不足"而非"一致/偏离",这是已知限制而非 bug。**2026-08-15 追加发现**:样本量小不是唯一原因——真实留一法交叉验证发现,即使有匹配的基准 case,`total_resistance_ohm`/`optimal_current_A`/`max_heat_dissipation_W` 这三个字段本身的模型预测误差就远超旧的 5% 容差(p90 89%-219%),两个问题叠加导致"consistent"实际上几乎只在把 benchmark 精确值原样回填当结果的测试流量里出现过(审计日志证实:历史所有 consistent 记录偏差都是精确 0)。容差已按字段校准(见上一条),但这三个字段本身的高误差指向的是 surrogate 模型需要更多训练数据或不同特征,不是这个服务能单独解决的。
- **竞赛/排序机制(若采用)归 Hermes 还是 ScienceRAG?** 已在实现中间接给出答案:归 Hermes。ScienceRAG 侧(M6 batch evidence,spec §3.4,`POST /sciencerag/priors/batch_evidence`)只按候选逐条给出支持/反驳/中立的证据分类,不做排序或打分,排序逻辑完全留给调用方。
- **候选更新包按什么格式提交给验证与版本治理?** ScienceRAG 侧的候选结构已定(`validate` 端点 `update_package`:`SurrogateUpdateSuggestion` + `KGCandidate` 列表,详见 `sciencerag/schemas/validate.schema.json`)。但这只是 ScienceRAG 自己的输出格式,是否匹配"第 02 部分"验证与版本治理期望接收的输入格式仍未确认——02 部分不在本规范范围内,需要跟负责该部分的同事对一下格式是否兼容。

## 10. 里程碑(建议)

M1:`priors` 端点(仅内部语料)+ schema 与回归测试集。M2:`validate` 的异常检查与结果评估上线(先做门槛,后做学习)。M3:微调建议与知识候选产出,打通候选更新包提交格式。M4:报告生成接入运行血缘。M5:GraphRAG `ask` 上线,答案附带子图;Web 前端(问答 + 图谱可视化 + 报告浏览)。M6:外部检索回退(Semantic Scholar + arXiv,开放获取全文下载即可信,无审批队列)+ 批量证据模式。
