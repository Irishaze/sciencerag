# ScienceRAG 整体设计规范 — TEC 世界模型闭环架构

## 1. 目的与范围

本规范描述 ScienceRAG 在 TEC 世界模型闭环架构中的完整设计,覆盖它在流水线中的全部四个接入点:

1. **前置文献检索**:在 Hermes 智能体编译实验规范之前,为其提供有文献依据的实验先验(即开始仿真前就能从文献与历史数据中知道的背景知识,如合理的参数取值范围、材料属性、预期性能区间,用于约束实验规范,避免从零盲猜)。
2. **验证与学习**:对仿真结果做异常检查与科学评估,并产出模型微调建议与知识库更新候选(即架构图中 "ScienceRAG 科学验证与学习" 的四个子模块)。
3. **报告生成**:输出带引用、可审计的实验报告。
4. **图谱问答**:支持用户基于科学知识图谱提问(GraphRAG,类 MiroFish 模式)。

不在范围内:Hermes 智能体本身、仿真适配器,以及第 02 部分的治理流程(验证与版本治理、模型与参数注册)。本规范将它们视为 ScienceRAG 输出的调用方或审批方:ScienceRAG 负责"提出",治理流程负责"批准"。

## 2. 总体架构与设计原则

ScienceRAG 是一组供 Hermes 调用的服务端点(endpoint,即服务对外暴露的可调用接口;每个端点对应一项独立能力,有固定的地址、输入格式与输出格式,Hermes 像调用工具函数一样按需请求),自身从不承担编排职责。四个端点按流水线顺序为:

`sciencerag.priors`(规划前) → `sciencerag.validate`(仿真后) → `sciencerag.report`(验证后) → `sciencerag.ask`(随时,面向用户)

贯穿所有组件的三条原则:

**严格结构化输出。** 所有响应在返回前经过 schema 校验,因此智能体绝不需要解析自由文本。校验失败时返回类型化错误,绝不返回不完整的 JSON。

**凡论断必有来源。** 每一条科学论断都携带来源引用:论文 DOI、知识图谱三元组 ID,或仿真运行 ID。

**只提议,不直写。** ScienceRAG 产出的任何内容都不直接写入知识图谱或模型注册表;所有知识与模型更新一律打包为候选更新包,经由第 02 部分的「离线验证 → 人工审批 → 注册/回滚」路径落地。

## 3. 组件 A — 前置检索(`sciencerag.priors`)

### 3.1 角色

由 Hermes 在任务规划阶段调用,时机在意图理解之后、结构化实验规范编译之前。职责是将研究问题转化为结构化的实验先验:合理的参数范围、材料属性、已知的标度关系,以及候选配置,每一项都以检索到的文献或内部知识图谱为依据。

### 3.2 检索流水线

内部流程遵循 PaperQA2 模式:查询分解 → 混合检索(稠密向量 + 关键词)覆盖论文库与科学知识图谱 → 逐块相关性打分的证据收集 → 结构化综合。知识图谱享有最高查询优先级,因为它包含系统自身历史运行的发现,而这是任何外部语料库都不具备的。优先级指查询顺序而非依赖:冷启动阶段图谱为空或极稀疏时,图谱查询命中 0 条,检索自动落到论文库与外部来源,端点照常返回(此时先验全部来自文献,`coverage` 中如实反映)。图谱随仿真运行与审批入库逐步积累。可选的冷启动加速("播种"):不等仿真攒数据,先跑一个一次性批处理任务,让 LLM 通读内部论文库,把文献中的关键结论逐条抽取成三元组(例如从某篇论文抽出"Bi₂Te₃ 薄膜在 300K 工况下 COP 达 1.5",来源挂该文 DOI),作为候选提交人工审批后入库。流程完全复用 4.4 已定义的"候选 → 审批 → 入库"路径,不引入新机制。效果是图谱从第一天起就有文献级的基础内容,`ask` 端点与 Web 前端上线即可用,不必空转等待仿真积累。

语料来源按优先级排列:内部知识图谱、内部论文库(项目维护的 TEC 文献集)、外部检索(Semantic Scholar / arXiv API)作为内部覆盖不足时的补充。外部结果标记为 `provenance: "external_unverified"`,以便下游按可信度加权处理。

### 3.3 工具接口

请求:

```json
{
  "query": "Bi2Te3 薄膜 TEC 中 COP 与热电臂几何的关系",
  "task_context": {
    "objective": "maximize_cop",
    "constraints": {"heat_load_w": 5, "ambient_k": 300}
  },
  "max_priors": 5,
  "allow_external": true
}
```

响应:

```json
{
  "status": "ok",
  "priors": [
    {
      "prior_id": "pr_2026_0713_001",
      "kind": "parameter_range",
      "field": "leg_length",
      "value": {"min": 0.02, "max": 0.2, "typical": 0.06, "unit": "mm"},
      "confidence": 0.82,
      "sources": [
        {"type": "paper", "doi": "10.1234/example", "span": "p.4, Fig.3"},
        {"type": "kg_triple", "triple_id": "kg_88213"}
      ],
      "notes": "臂长偏短有利于功率密度;COP 在中段区间达到峰值。"
    }
  ],
  "coverage": {"internal_hits": 7, "external_hits": 2, "gaps": ["接触电阻数据稀缺"]},
  "trace_id": "tr_..."
}
```

`kind` 为枚举类型:`parameter_range`(参数范围)、`material_property`(材料属性)、`scaling_relationship`(标度关系)、`candidate_config`(候选配置)、`caution`(注意事项)。`gaps` 字段是刻意设计的:Hermes 需要知道文献中*未*覆盖的部分,从而在这些区域扩大仿真扫描范围,而不是盲信一个证据薄弱的先验。`field` 与可选字段 `related_fields` 的取值均来自仿真参数契约(见 3.6);`material_property` 保留枚举值但因材料固定而实际不产出。

### 3.4 与假设排序的配合

若团队采用类 AI co-scientist 的「生成—辩论—排名」竞赛机制,竞赛逻辑归属于 Hermes(或其平级工具),而非本服务。本服务通过批量证据请求为其提供支撑:给定 N 个候选实验规范,逐一返回支持性与反驳性证据,使排序器(Elo/BTL)能够基于文献依据而非模型直觉来打分。

### 3.5 论文库入库流程

内部论文库通过一条离线入库流水线维护,与在线端点分离,按批运行:

1. **收集**:两个来源。团队手动加入的文献(共享目录或上传入口);以及组件 A 外部检索命中的文献,自动进入本流水线存入库中,但携带 `external_unverified` 标签(检索可用,计算 confidence 时降权)。外部文献升级为"可信"有两条路:人工确认,或满足预设规则自动转正(如来自期刊/会议白名单,且被内部检索重复命中达到阈值);规则由团队制定,人工只处理规则覆盖不到的情形。原则与图谱一致:存储自动化,信任须把关。
2. **解析**:从 PDF 抽取正文、章节结构与元数据(标题、作者、年份、DOI)。v1 仅支持文字版 PDF,扫描版拒收并记录日志。
3. **切块**:按章节边界切分为数百 token 的片段,相邻片段留重叠;每个片段携带元数据(DOI、页码、章节),这是响应中 `sources` 能精确定位到页与图的前提。
4. **向量化入库**:片段经 embedding 模型转为向量,连同原文与元数据存入向量库;按 DOI 去重,重复上传只更新。

约束:embedding 模型版本与向量库绑定记录;更换模型时必须全库重建,禁止新旧向量混存。入库流水线的运行记录(何时入了哪些文献、解析成功/失败)纳入审计日志。

### 3.6 仿真参数契约(sim_params.json)

先验的 `field` 并非自由文本:它的取值空间由一份与仿真侧(COMSOL 单级 Bi2Te3 TEC)对齐的参数契约 `sim_params.json`(`sciencerag/priors/sim_params.json`)固定,避免 Hermes 在把先验填入仿真时还要做一次名称/单位翻译——例如先验侧曾自造 `leg_length_um` 这样的命名,仿真侧实际叫 `leg_length` 且单位是 mm,人工翻译容易出错,也让先验与仿真结果按参数对比时对不上。

契约把仿真参数分为五类,并各自标注 `prior_target`:

- **`geometry_free`(自由几何参数,`prior_target: true`)**:Hermes 主动优化/扫描的对象,是先验唯一的目标,共 12 个——`leg_length`、`leg_width`、`pitch`、`d_conductor`、`d_ceramics`、`length`、`width`、`height`、`sink_base_h`、`sink_fin_h`、`sink_fin_w`、`sink_fin_n`,每个参数带真实仿真参数名与单位。
- **`material`(材料,`prior_target: false`)**:材料固定为 Bi2Te3,属性(Seebeck 系数、电阻率、热导率、优值 Z)随温度变化,按 200–400K 的整张表登记为已知常量;先验不对材料出建议。
- **`operating_condition` / `derived` / `numerical_setting`(均 `prior_target: false`)**:分别是任务给定的工况、由其他参数算出的派生量、纯数值求解设置,均与先验无关。

`Prior` 模型上,单参数先验(`parameter_range`/`caution`)用 `field`;新增的可选字段 `related_fields`(默认空列表,向后兼容)供多参数先验(`scaling_relationship`/`candidate_config`)表达"一组参数"或"参数之间的关系"。两者取值都必须 ∈ 契约 `geometry_free` 的参数名集合,抽取流水线在解析 LLM 输出后强制校验,不在集合内一律拒绝——防止 LLM 自造名称,或误碰材料/工况/派生参数。抽取本身也是目标导向的:提示词把这 12 个参数名与单位直接列给 LLM 作为清单,而非任其自由命名;参数之间的关系不预设分组,只有证据里实际提到才抽成 `scaling_relationship`,文献没提就不造。

`kind` 五值枚举本身不变,但 `material_property` 在当前项目实际上是"存在于枚举、但从不产出"的状态:材料固定且属性已知,先验不对它出建议;若 LLM 仍误输出材料类先验,抽取流水线会将其过滤,不进入响应,但计入审计日志(而非 `coverage.gaps`——这不是"漏检覆盖",而是"被正确排除")。

`coverage.gaps` 同样以契约的 12 个几何参数为标尺:本次抽取覆盖了哪些、没覆盖哪些,没覆盖的进 `gaps` 而不是硬凑一个先验去凑数。v1 先给出"未覆盖"这一简化归因;更细的"未检索到证据 / 检索到但相关性不足 / 抽到但置信度不足"三级归因留待后续迭代。

五种 `kind` 在契约体系下的填法:

| kind | field | related_fields | value 要点 |
|---|---|---|---|
| `parameter_range` | 恰好一个契约参数名(必填) | 不填 | 至少一个数值键,如 `{"min", "max", "typical", "unit"}` |
| `material_property` | 恒为 `null` | 不填 | 材料属性固定见契约,不由先验提供;实际不产出 |
| `scaling_relationship` | `null` 或标主参数 | 关系涉及的参数列表(至少一个) | 含 `direction`(`positive`/`negative`/`convex`/`unknown`)与说明 |
| `candidate_config` | 恒为 `null` | 这组配置涉及的参数列表 | 按参数名给出这组配置的每个值 |
| `caution` | 通常填一个参数;涉及多参数时用 `related_fields` | 视情况 | 限制/注意事项说明 |

### 3.7 阈值调优方法论(检索 k / 证据相关性 / 先验置信度)

检索流水线有三道独立的筛选关卡:检索侧的 top-k 截断、证据相关性阈值 `MIN_EVIDENCE_RELEVANCE`、先验置信度阈值 `CONFIDENCE_THRESHOLD`。某个契约几何参数在某次查询中"没有先验",可能来自三种不同原因——文献本身没有相关内容(真 gap,应保留,是留给 Hermes 扩大仿真扫描的有效信号);或文献本有相关内容,却被 k / 相关性 / 置信度中的某一关卡筛掉(假 gap,应通过校准各关卡消除,而不是靠调低阈值把噪声一并放进来)。三道关卡各自独立调优,不能用后一道关卡的阈值去补前一道关卡的问题——例如置信度阈值治不好因 k 太小或相关性阈值太严导致的漏检。

调优顺序:先放开检索侧的 top-k(用不同 k 下 12 个几何参数的覆盖率曲线找拐点,而非盲目调大——k 越大,进入摘要/抽取阶段的候选证据越多,成本与噪声也随之上升);再在新 k 与目标导向抽取(见 3.6)下重新采集探针数据,保留每条证据/先验筛选前的原始分数(不因阈值静默丢弃,否则无法回溯误杀);再依次校准相关性阈值与置信度阈值,两者都采用"独立 LLM 裁判"方法——对处于阈值边界带的证据/先验样本,由与生产链路模型无关的裁判模型(GPT-4o,`temperature=0`,保证可复现)逐条判定应保留还是丢弃,裁判规则须能识别"证据实为参考文献列表标题、并非论文正文"这类已知的误报模式,再按分数分桶统计误判率曲线,在"漏检率"与"噪声纳入率"之间取平衡点。全程用真实数据验证,不凭经验直接定阈值;探针与裁判所需的记录只在启用 trace 的探针路径中产生,生产查询路径的行为不变。

`coverage.gaps` 最终应对每条未覆盖参数标注筛选层级归因(未检索到证据 / 检索到但相关性不足 / 抽到但置信度不足),使 Hermes 能区分"真无先验"与"流水线筛掉的弱信号",而非把两者混为一谈的笼统"未覆盖"。

## 4. 组件 B — 验证与学习(`sciencerag.validate`)

对应架构图中「ScienceRAG 科学验证与学习」的四个子模块。调用时机在潜在世界状态创建之后:即一次运行走完 04 仿真 → 05 结果标准化 → 06 潜在状态编码全部三步后,由 Hermes 调用一次。定在这个时点是因为三类异常检查中,守恒与 PDE 残差只依赖 05 的标准化结果,而 OOD 检测必须依赖 06 产出的潜在状态 z;以最晚的依赖为准、单次调用,架构最简。四个子模块按固定顺序运行,前一级是后一级的门槛:

异常检查 → 结果评估 → (并行)模型微调建议 + 知识库更新 → 组装候选更新包

### 4.1 异常检查

**职责:** 判断这次运行的结果在物理上是否可信,不可信的结果不允许进入任何学习环节。

三类检查依次执行:

1. **守恒检查**:对温度场与热流场做能量平衡核算,残差超出阈值即告警。
2. **PDE 残差**:将求解结果代回控制方程(热电耦合 PDE),计算残差范数,用于捕捉"收敛了但收敛到错误解"的情况。
3. **OOD 检测**:将本次运行的潜在状态 z 与历史运行分布对比(马氏距离或基于密度的评分),显著偏离即标记为分布外。分布外不等于错误,但意味着代理模型的预测在此不可信,需降权处理。

**输出:** 类型化的异常列表,每条含 `check`(检查项)、`severity`(`info` / `warning` / `blocking`)、`evidence`(具体数值与阈值)。任何 `blocking` 级异常都会短路后续所有环节:运行结果只进入报告(标注失败原因),不产出微调建议,不产出知识候选。这条规则是本组件最重要的设计决策:宁可少学,不可学错。

### 4.2 结果评估

**职责:** 通过了异常检查的结果,进一步回答"这个结果科学上说得通吗"。

两条对照线:

1. **基准对比**:与基准数据库中的已知案例(解析解、高保真 FEniCSx 参考解、实验数据)对比,量化偏差。
2. **先验对比**:与组件 A 在规划阶段提供的文献先验对比。结果落在先验范围内,是一次常规确认;结果显著偏离先验,则是本次运行最有信息量的发现,需要在输出中显式标出并附上双方证据(先验的文献来源 vs 本次运行的数据),交给人来裁断是"文献错了 / 先验检索有偏 / 仿真有问题"。这一步是前置检索与后置验证之间的闭环,也是整个 ScienceRAG 设计里检索真正产生科学价值的地方。

**输出:** 评估结论(`consistent` / `deviation_found` / `insufficient_benchmark`)、逐项偏差数据、证据引用。

### 4.3 模型微调建议

**职责:** 面向代理模型(PhysicsNeMo 系的 SepONet / FNO / MeshGraphNet 等)提出改进建议;只提建议,不执行训练。

依据两类信号选样:代理模型预测与高保真求解结果偏差最大的区域(误差驱动),以及 OOD 检测标记的分布外区域(不确定性驱动,即主动学习的思路)。建议内容包括:推荐纳入训练集的样本清单(以运行 ID + 区域标识表示)、建议的损失加权、超参数调整方向及理由。

**输出:** 微调提案,进入候选更新包的 `surrogate_update` 字段。是否执行、何时执行,由第 02 部分的治理流程与人工审批决定。

### 4.4 知识库更新

**职责:** 从通过评估的运行结果中抽取候选三元组(材料—结构—工况—性能),供知识图谱审批入库。

流程:从结果与评估结论中抽取候选关系 → 与图谱中现有三元组做去重与冲突检测(同一关系已存在且一致 → 仅追加来源;存在但数值冲突 → 标记冲突,双方来源并列呈现,不自动覆盖)→ 为每条候选附上完整溯源(运行 ID、置信度、支撑数据切片),即架构图中的「来源审查」所需材料。

**输出:** 候选三元组列表,进入候选更新包的 `kg_candidates` 字段。与组件 D 的只读约束呼应:写入图谱的唯一路径是审批通过。

### 4.5 组件接口(概要)

请求:`run_id` + 标准化结果引用 + 潜在状态引用 + 本次运行使用的 `prior_id` 列表。响应:

```json
{
  "status": "ok",
  "anomalies": [{"check": "energy_balance", "severity": "warning", "evidence": {...}}],
  "evaluation": {"verdict": "deviation_found", "deviations": [...], "sources": [...]},
  "update_package": {
    "surrogate_update": {...},
    "kg_candidates": [...],
    "blocked": false
  },
  "trace_id": "tr_..."
}
```

`blocked: true` 时 `surrogate_update` 与 `kg_candidates` 必为空,这是 schema 层面强制的不变量,不依赖调用方自觉。

## 5. 组件 C — 报告生成(`sciencerag.report`)

在验证完成后调用。输入包括标准化结果、组件 B 的完整输出(异常、评估、更新提案),以及规划阶段使用的先验。输出一份 JSON 文档外加渲染后的 Markdown/PDF 视图。

必备章节:系统所理解的目标与约束;实验规范摘要;带不确定度的关键结果;与文献先验的对比(直接引用组件 B 4.2 的评估结论);异常与注意事项;更新提案摘要(本次运行建议了哪些微调与知识候选,便于审批者从报告直达审批);完整引用列表。报告正文中的每一条定量论断都附带指向运行 ID 或文献来源的行内引用。报告随运行血缘版本化存储,使第 02 部分的注册表能够将模型更新回溯到促成它的那份报告。

## 6. 组件 D — 图谱问答(`sciencerag.ask`)

### 6.1 知识图谱

复用现有科学知识图谱的 schema:实体为材料、结构、工况与性能指标;边为带类型的关系,每条边携带来源(论文 DOI 或运行 ID)与置信度。v1 无需修改 schema。

### 6.2 查询流程

类 MiroFish 模式:用户提问 → 实体/关系抽取 → 图谱遍历组装相关子图 → 子图与问题一并送入 LLM 进行有据可依的答案合成 → 返回答案并附带子图,供前端渲染「依据是什么」(关系可视化、来源·置信度)。若图谱覆盖不足,服务如实说明,并可选择回退到组件 A 的文档检索,回退情况在响应中明确标注。

### 6.3 写入路径(关键约束)

`sciencerag.ask` 与 `sciencerag.report` 对图谱均为只读。新知识进入图谱的唯一路径是组件 B 4.4 产出的候选三元组通过验证与版本治理。这一约束防止单次异常运行污染所有后续检索,相当于「静默解析 bug 向下游扩散」这一问题在知识层面的对应物。

## 7. 呈现层 — 交互式 Web 前端(类 MiroFish)

组件 C 与 D 的用户入口是一个 Web 应用(Vite/React 前端 + Flask/FastAPI 后端,后端仅做端点转发与会话管理)。页面分三个区域:

1. **问答面板**:用户提问,调用 `sciencerag.ask`。
2. **图谱可视化**:渲染 `ask` 返回的子图(力导向布局,节点可点击查看来源与置信度),用户提问后相关子图高亮,直观呈现「答案依据是什么」。
3. **报告面板**:按运行血缘浏览与导出历史报告。
4. **文献审批面板**:处理 3.5 节的外部文献转正队列,仅对管理层角色开放(前端按角色隐藏入口,后端在审批相关接口上强制校验权限;普通用户即使拿到接口地址也无法调用)。每条待办展示文献元数据(标题、期刊、年份、DOI 链接、摘要)、被检索命中的记录,以及风险提示(如不在期刊白名单);审批人判断的是来源资质而非科学内容,操作为批准 / 拒绝 / 搁置,每次操作记录操作人、时间与理由,纳入审计日志。v1 可用命令行脚本替代页面,流程不变。

注意:图谱本身由仿真闭环持续积累产生,提问只是从全图中提取并展示相关子图,前端不创造知识。前三个面板只调用只读端点;文献审批面板仅写入论文库的信任标签,不触碰知识图谱,第 6.3 节的约束不受影响(三元组入图谱与模型微调的审批属于第 02 部分的验证与版本治理,不在本前端范围内)。可选扩展:针对一段问答会话生成小结报告,复用 `report` 的引用机制。

## 8. 通用要求

四个端点均返回经 schema 校验的 JSON,并携带 `trace_id`,将请求、证据与响应串联以供审计。错误采用类型化定义(`retrieval_timeout`、`schema_validation_failed`、`insufficient_coverage`、`benchmark_unavailable` 等),使 Hermes 能够确定性地分支处理。

延迟目标:`priors` ≤ 30 秒(阻塞规划)、`validate` ≤ 60 秒(阻塞闭环推进,其中守恒/残差检查为主要开销)、`ask` ≤ 10 秒(交互式)、`report` 为尽力而为的批处理。

评估机制是维护一套固定的回归测试集:检索侧为(查询 → 带已知来源的预期先验/答案),验证侧为(已知有缺陷的历史运行 → 预期异常判定,含应当 `blocking` 与不应误伤的两类案例)。度量引用准确率、覆盖率、schema 合法率,以及异常检查的查全/查准;每次修改提示词、检索参数、阈值或语料库后必须运行。

## 10. 里程碑(建议)

M1:`priors` 端点(仅内部语料)+ schema 与回归测试集。M2:`validate` 的异常检查与结果评估上线(先做门槛,后做学习)。M3:微调建议与知识候选产出,打通候选更新包提交格式。M4:报告生成接入运行血缘。M5:GraphRAG `ask` 上线,答案附带子图;Web 前端(问答 + 图谱可视化 + 报告浏览 + 文献审批面板,审批 v1 可先以命令行脚本形态随 3.5 入库流水线上线)。M6:外部检索回退 + 批量证据模式。
